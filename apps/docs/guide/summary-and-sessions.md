# 全文总结与多轮会话

## 为什么旧版会漏掉核心内容

“总结文档”不是普通 Top-K 问答。普通检索寻找与一句 Query 最相似的少量片段，而总结需要摘要、
方法、实验和结论等互补证据。即使 PDF 已正确解析，Reranker 也可能把关键词密集的参考文献排在
前面，最终模型只能看到局部内容。

UltimateRAG 现在会在 Trace 中区分：

| 意图 | 策略 | 适用问题 |
|---|---|---|
| `fact` | `ranked_retrieval` | 定义、参数、步骤、局部事实 |
| `document_summary` | `structural_coverage` | 总结整份文档、论文核心内容 |

全文总结直接读取 PostgreSQL 中 READY 文档的 Chunk，按章节覆盖并排除 References 等尾部噪声。
界面的检索证据会显示“全文总结 / 章节覆盖”，方便确认路由是否正确。

## 会话如何工作

每次进入知识库问答页都会建立一个新会话。顶部可以：

- 点击“新会话”开始独立上下文；
- 从历史下拉框选择旧会话继续；
- 切换知识库时自动建立该知识库的新会话。

会话严格绑定知识库，后端会再次校验 `session_id` 与 `knowledge_base_id`，不能通过前端参数串用。
首个问题会自动成为会话标题，避免额外调用模型生成标题。

## 长上下文处理

PostgreSQL 永久保存原始消息。进入模型 Prompt 的内容则分为：

```text
较早消息 → 百炼递归摘要 → 长期对话记忆
最近消息 → Token 预算内原文保留
当前问题 → 会话感知 Query Rewrite → 本轮知识检索
```

长期摘要只帮助理解“它”“上一个方案”等指代，以及用户约束、偏好和未决问题；它不是知识库
事实。最终回答仍只能引用本轮检索得到的 `knowledge_context`。摘要服务临时失败时，系统继续使用
最近原文，原始历史不会丢失。

## 流式一致性

发送问题后，数据库先写入用户消息和 PENDING 助手占位。只有模型流完整结束才把助手消息提交为
COMPLETE；网络断开或生成失败会留下可见 FAILED 状态。同一会话一次只允许一个回答生成，避免
两条流交叉污染历史顺序。
