# UltimateRAG V3 Advanced Retrieval 实现说明

## 1. 目标与范围

V3 解决“能搜到，但排序不够准”。它在 V2 文档智能和异步摄取之上实现：

- Dense Retrieval
- Milvus 原生 BM25 Sparse Retrieval
- Hybrid Search 与 RRF
- 百炼 Query Rewrite 和 Reranker
- Knowledge Base + Document Metadata Filter
- Parent-Child / Small2Big Context
- 独立 Retrieval Explain API 与轻量离线指标

V3 不实现 ACL、多租户、审计、DLQ 控制台、在线 RAGOps、Agent/GraphRAG。详细技术决策见
[ADR-002](adr/ADR-002-v3-hybrid-retrieval.md)。

## 2. 查询主链路

```text
Original Query
    │
    ├── optional Query Rewrite（原查询永远保留）
    │
    ├───────────────┬────────────────┐
    ▼               ▼                │
Dense / COSINE   Sparse / BM25       │ 每个查询变体
    └───────────────┴────────────────┘
                    ▼
              RRF（默认 k=60）
                    ▼
          Candidate Pool（默认 30）
                    ▼
       qwen3-rerank（最终 top_k）
                    ▼
     Small2Big Parent Context（±1 Child）
                    ▼
          Context Builder → LLM → Citation
```

`RetrievalService` 位于 `application/retrieval.py`，流程从上到下显式可读，不使用 LangGraph。
`search()` 保留旧列表接口，`retrieve()` 同时返回 `RetrievalRun(results, trace)`。

## 3. Dense 与 Sparse 索引

### Dense

V2 `knowledge_chunks` 保持不变：`text-embedding-v4` 1024 维、COSINE、AUTOINDEX、稳定 Chunk ID。

### Sparse

V3 新增 `knowledge_chunks_sparse_v3`：

| 字段 | 类型 | 用途 |
|---|---|---|
| `id/chunk_id` | VARCHAR | 稳定 Child Chunk ID |
| `knowledge_base_id` | VARCHAR | 强制检索隔离 |
| `document_id` | VARCHAR | 文档白名单过滤 |
| `filename` | VARCHAR | Citation 展示 |
| `content` | VARCHAR + Analyzer | BM25 原文输入 |
| `heading_path` | JSON | SourceLocator 兼容数据 |
| `sparse_embedding` | SPARSE_FLOAT_VECTOR | Milvus BM25 Function 输出 |

Analyzer 固定为 `jieba + lowercase`，兼顾中文词边界和英文技术词。Sparse 向量由本地 Milvus 生成，
不是百炼线上服务。新文档先写 Dense、再写 Sparse，全部成功后才 `READY`；失败补偿同时清理两边。

## 4. 历史数据升级

启动新代码会幂等创建 Sparse Collection，但不会在应用启动时进行昂贵或隐式数据迁移。V1/V2 历史
Chunk 使用以下命令回填：

```bash
uv run python scripts/rebuild_sparse_index.py
```

脚本从 PostgreSQL 以稳定 Chunk ID 做 Keyset Pagination，每批默认 500 条，只执行 Sparse Upsert，
不调用 Embedding。若只需精确重建一个知识库：

```bash
uv run python scripts/rebuild_sparse_index.py \
  --knowledge-base-id <knowledge-base-id> \
  --replace
```

`--replace` 必须提供知识库 ID，而且只删除该知识库的 Sparse 行，不触碰 Dense 与事实数据。
为了避免与 Worker 的跨存储写入形成删除竞态，知识库仍有非终态摄取任务时会拒绝 `--replace`。

## 5. Query Rewrite

默认模型 `qwen-plus`，要求 JSON Object：`{"query":"..."}`。规则包括：

1. 用户 Query 被包在数据标签中，不能覆盖系统角色或输出格式。
2. 只生成一个变体，不做无界多查询扩增。
3. 必须保留产品型号、版本号、数字、日期和专有名词。
4. 原查询总是参与检索，改写只做补充。
5. 空响应、非法 JSON、字段越界或服务故障都会回退原查询，并写入 Trace。

## 6. RRF 与分数语义

COSINE 和 BM25 的原始分数不能比较。两个以上排名列表使用：

```text
RRF(d) = Σ 1 / (k + rank_i(d)), default k = 60
```

每个 `RetrievalResult` 保留：

- `dense_score`
- `sparse_score`
- `fusion_score`
- `rerank_score`
- `score`：当前最终排序实际使用的分数
- `retrieval_sources`：例如 `dense:original`、`sparse:rewrite`

这些值用于解释一次请求内的排序，不能跨模式或跨请求当作统一概率。

## 7. Reranker

默认 `qwen3-rerank` 使用百炼兼容接口。阿里云已在 2026-05-30 停止 `gte-rerank-v2`，因此旧模型
只保留显式配置的协议兼容，不再作为可运行默认值。应用把融合后的有限候选一次批量提交，
`top_n` 等于最终 API `top_k`。Adapter 按官方公式
`query_tokens × document_count + total_document_tokens` 估算总量，在 120,000 Token 上限内再预留
10% tokenizer 误差余量；预算不足时保留 RRF 排名靠前的候选前缀。单条正文只在 Rerank 请求副本中
做有界截断，原 Chunk 与 Citation 不变；超长 Query 不截断，而是触发可观察降级。Adapter 还校验：

- 响应 JSON 结构
- index 必须落在请求候选范围
- index/Chunk ID 不能重复
- 至少返回一个结果

失败时不无限重试，而是保留 RRF 顺序，并在 Trace 标记 `rerank_failed`。

## 8. Metadata Filtering 与状态一致性

请求可传最多 50 个 `document_ids`。流程是：

1. PostgreSQL 求 `knowledge_base_id + READY + requested IDs` 交集。
2. 交集为空时立即返回，不调用 Embedding、Milvus、Rewrite 或 Rerank。
3. 非空交集同时下推 Dense 和 Sparse 的 Milvus 标量过滤。
4. 所有 Hit 再按 PostgreSQL READY 集合二次过滤。

Milvus Filter 的字段名/操作符固定，值使用 JSON 编码转义，不直接拼接不可信引号。

## 9. Parent-Child / Small2Big

V3 Chunk metadata 新增：

```json
{
  "parent_id": "stable-uuid",
  "parent_child_index": 1,
  "parent_child_count": 3
}
```

Parent 是 Parser/Chunker 恢复的语义 Section，Child 仍遵守 512 Token 检索预算。召回 Child 后，
Repository 用两条批量 SQL 读取全部命中及有界邻居；应用只保留同 Parent、前后各一个 Child，并执行
默认 1536 Token 总预算。最终结果中：

- `chunk_id` 和 Citation 仍指向真正命中的 Child；
- `matched_content` 保存原命中正文；
- `content` 是最终进入 Context 的扩展正文；
- `context_chunk_ids` 列出实际使用的所有 Child。

历史 Chunk 没有 `parent_id` 时，按同标题路径、页码、Sheet/Range、Slide 严格回退，绝不跨页/跨节。

## 10. API

兼容端点：

```text
POST /api/retrieval/search  -> RetrievalResult[]
```

V3 调试端点：

```text
POST /api/retrieval/explain -> { results, trace }
```

请求可选字段：

```json
{
  "knowledge_base_id": "kb-id",
  "query": "Milvus 的 BM25 参数是什么？",
  "top_k": 5,
  "mode": "hybrid",
  "candidate_k": 30,
  "enable_query_rewrite": true,
  "enable_rerank": true,
  "enable_parent_expansion": true,
  "document_ids": ["optional-document-id"]
}
```

Chat 非流式响应和 SSE `data-retrieval` 都携带同一份 `retrieval_trace`，不会重新执行一次检索。

## 11. 降级矩阵

| 故障 | 行为 |
|---|---|
| Rewrite 失败 | 使用原查询，Trace 记录 `query_rewrite_failed` |
| Hybrid 单通道失败 | 使用另一通道，记录 Dense/Sparse failure |
| 所有请求通道失败 | 请求失败，不能伪造无结果 |
| Reranker 失败 | 保留 RRF/单通道排名，记录 `rerank_failed` |
| Parent 扩展失败 | 使用命中 Child 正文，记录 `parent_expansion_failed` |
| PostgreSQL 事实读取失败 | 请求失败，不能绕过 READY/业务范围约束 |

## 12. 离线评估

`scripts/evaluate_retrieval.py` 读取人工标注 JSONL，通过公开 API 计算：

- Precision@k
- Recall@k
- MRR@k
- binary nDCG@k

```bash
uv run python scripts/evaluate_retrieval.py eval.jsonl --mode hybrid --k 5
uv run python scripts/evaluate_retrieval.py eval.jsonl --mode dense --disable-rerank
```

这支持 Dense/Sparse/Hybrid 和 Rewrite/Rerank 消融。Small2Big 不改变 Chunk 排名指标，因此评估脚本
默认关闭它，只有验证上下文读取时才传 `--enable-parent-expansion`。工具不冒充 V5 的 Golden Dataset
管理与在线 RAGOps。

## 14. 已知限制

- BM25 Analyzer/参数变化需要显式重建 Sparse Collection，应用不会在线改 Schema。
- V3 只开放 Document ID Filter；ACL、组织/用户权限和多租户属于 V4。
- Parent 扩展使用有限相邻 Child，不会无界返回整个超长章节。
- Query Rewrite/Rerank 是线上百炼调用，需评估延迟、费用和限流；Sparse 分词与 BM25 在本地 Milvus。
- 默认参数是公开实践基线，不是对任意企业数据集的“最佳值”。

Rerank 模型状态、请求字段和 Token 限制以
[阿里云百炼 Rerank 官方文档](https://help.aliyun.com/en/model-studio/rerank) 与
[Text Rerank API](https://help.aliyun.com/en/model-studio/text-rerank-api) 为准。
