# UltimateRAG V1 实现说明

## 1. 文档目的

本文解释 V1 代码如何把产品文档中的 Naive RAG 设计落为一个完整工程，并帮助学习者沿调用链阅读代码。
产品范围以 `1.product_description.md` 为准，整体架构以 `2.technical_architecture.md` 为准。

## 2. V1 验收闭环

```text
创建知识库
  ↓
上传 Markdown
  ↓
MinIO 保存原文件 + PostgreSQL 保存文档事实
  ↓
MarkdownParser → ParsedDocument / Block
  ↓
StructureAwareMarkdownChunker → Chunk
  ↓
百炼 text-embedding-v4
  ↓
Milvus knowledge_chunks
  ↓
Dense Retrieval
  ↓
ContextBuilder → 百炼 qwen-plus
  ↓
Answer + Citation + Retrieval Results
```

## 3. 分层与依赖方向

### Domain

`src/ultimate_rag/domain` 定义领域模型、状态和可替换端口。它不导入任何 Web、数据库、向量库或模型 SDK。
这保证业务概念不会变成某个框架的数据结构。

核心模型：

- `DocumentSource`：解析器输入的原始字节快照
- `ParsedDocument` / `Block`：统一文档模型
- `Chunk`：稳定、可引用的检索单元
- `EmbeddedChunk`：写向量库前的临时组合
- `RetrievalResult`：带来源定位的召回结果
- `Citation`：面向最终用户的引用

### Application

`src/ultimate_rag/application` 以普通 Python Service 显式编排确定性流程。V1 不需要 LangGraph，因为当前没有
条件路由、循环、Agent 决策或 Human-in-the-loop。

### Infrastructure

外围适配器负责把领域端口映射到具体技术：

- `Repository` → SQLAlchemy / PostgreSQL
- `MinioObjectStorage` → MinIO SDK
- `MilvusVectorStore` → PyMilvus
- `BailianEmbedder` / `BailianLLMClient` → OpenAI 兼容 API

### Interface

FastAPI 路由只验证请求、调用应用服务、映射响应。Next.js 只负责产品交互，不承载 RAG 核心逻辑。

## 4. 文档摄取调用链

入口是：

```text
POST /api/knowledge-bases/{id}/documents
```

`IngestionService.ingest()` 的顺序具有明确含义：

1. 确认知识库存在
2. 只接受 `.md` / `.markdown`
3. 校验 Markdown 扩展名、常见 MIME、空文件和 10 MB 大小限制
4. 使用 UUID 构造 MinIO Object Key，避免路径穿越
5. 保存原文件
6. 创建 `PENDING` 文档事实记录
7. 依次更新 `PARSING`、`CHUNKING`、`EMBEDDING`、`INDEXING`
8. 在 PostgreSQL 中替换 Chunk，使重试不产生重复事实数据
9. 按文档删除旧向量，再以稳定 Chunk ID upsert，并显式 flush 持久化
10. 所有必要步骤成功后更新 `READY`

任何处理阶段失败都会写入 `FAILED` 和可理解错误信息。原始文件继续保留，为排查和未来索引重建提供依据。

## 5. Markdown 解析与结构感知切块

`MarkdownParser` 使用 CommonMark Token 识别标题、普通文本和代码块。它不输出 HTML，也不使用 LangChain
Document，而是生成 UltimateRAG 的 `ParsedDocument`。

每个 Block 带有 `heading_path`，例如：

```json
{"heading_path": ["RAG", "Embedding", "BGE-M3"]}
```

切块优先按章节聚合。只有章节超过配置的字符预算时，才做带 overlap 的二次切分。Chunk ID 由
`document_id + chunk_index + content` 派生，因此相同文档内容重新处理会得到相同 ID。

V1 的 `token_count` 是用于观察的保守估算，不宣称等于模型分词器的精确值。模型 API 仍是最终输入限制边界。

## 6. Embedding 与 Milvus

默认向量模型为 `text-embedding-v4`，维度为 1024。适配器遵守模型每批最多 10 条文本的限制，并验证：

- 响应向量数量等于输入数量
- 响应顺序按 API index 恢复
- 每个向量维度等于配置值

Milvus Collection 为 `knowledge_chunks`。字段包含：

```text
id / chunk_id
knowledge_base_id
document_id
filename
content
heading_path
embedding
```

检索使用 COSINE。查询必须带 `knowledge_base_id` Filter，避免跨知识库召回。
写入和删除都会显式调用 flush，因此应用层只有在 Milvus 接受并持久化变更后才继续返回成功或推进 `READY`。
需要注意，Milvus Collection 的物理 `row_count` 可能暂时包含等待 compaction 的删除 tombstone；判断当前可见实体应使用强一致 query/search，而不是直接把物理行数当成业务事实。

## 7. Retrieval 与 RAG 的解耦

`POST /api/retrieval/search` 不调用 LLM，可以独立验证召回质量、分数、章节和 Chunk 内容。这是 RAG 工程中
非常重要的调试边界：答案错误时，可以先判断是“没有召回”还是“生成没有正确使用证据”。

`POST /api/chat` 在 Retrieval 之后执行：

1. `ContextBuilder` 按召回顺序加 `[来源 N]` 标签
2. 在字符预算内拼接上下文
3. 系统 Prompt 把检索内容声明为不可信数据
4. LLM 只根据标签内知识回答
5. 应用层直接从 Retrieval Result 构造 Citation

Citation 不依赖 LLM 自己生成，因此文档 ID、Chunk ID 和标题路径可追溯且稳定。

## 8. 数据一致性取舍

V1 是同步 MVP，不引入分布式事务、消息队列或补偿 Worker。采用以下简单策略：

- MinIO 与 PostgreSQL 是事实来源
- Milvus 是派生索引
- 外部阶段失败时记录明确 `FAILED`
- Chunk 替换和数据库状态更新各自使用单库事务
- 向量写入使用稳定 ID upsert
- 删除操作先清理派生向量和原文件，最后删除事实记录；失败会向上抛出

V4 才会增加可靠重试、任务队列、死信和更完整的补偿机制。

## 9. 安全边界

V1 已实现：

- 扩展名、大小、空内容和 UTF-8 编码校验
- 用户文件名只保留 basename，不用于 Object Key
- API Key 只从项目 `.env` 读取，Compose 使用 `env_file` 注入，避免开发机同名环境变量覆盖
- `.env` 被 Git 忽略
- Prompt 明确隔离不可信知识内容
- 客户端错误不返回 Stack Trace

V1 尚未实现认证、ACL、租户隔离、审计和公网限流。生产公网部署前必须增加这些企业能力。

## 10. 如何阅读与调试

推荐顺序：

1. `domain/models.py`：理解业务数据
2. `domain/ports.py`：理解可替换边界
3. `application/services.py`：阅读两条主工作流
4. `parsers/markdown.py` 与 `chunkers/markdown.py`：理解文档结构进入 RAG 的方式
5. `embeddings/bailian.py` 与 `vectorstores/milvus.py`：理解向量化和检索
6. `application/context.py` 与 `generation/bailian.py`：理解生成边界
7. `apps/api/routes.py`：理解外部 API
8. `apps/web`：理解用户如何操作完整闭环

调试建议：

- 文档失败：先查看 API 日志和文档 `error_message`
- 没有召回：使用“检索调试”确认向量结果，再通过 Attu 查看 Collection
- 回答不准：比较 Retrieval Results 与最终答案，区分检索问题和生成问题
- 原文件问题：在 MinIO Console 查看 `documents` Bucket
- 状态问题：在 PostgreSQL 检查 `documents` 与 `chunks`

## 11. 测试边界

单元测试覆盖 Markdown 解析、结构感知切块、稳定 Chunk ID、上下文预算、Parser Registry、百炼批次行为、
CORS 配置解析和 Milvus 写入/删除后的 flush 顺序。
`tests/fixtures/rag.md` 是固定 Smoke Test 文档。

完整端到端验证需要 Docker 服务和有效百炼配置，验证顺序为：

```text
Create KB → Upload Fixture → Document READY → Retrieval Hit → Chat Citation
```

这条链路同时证明 PostgreSQL、MinIO、Milvus、Embedding 和 LLM 已正确协作。
