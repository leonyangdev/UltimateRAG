# UltimateRAG 产品定位文档

## 1. 产品名称

**UltimateRAG**

英文定位：

> **An evolvable enterprise-grade RAG platform.**

中文定位：

> **一个从最小可用 RAG 持续演进为企业级智能知识平台的开源项目。**

UltimateRAG 不以“堆砌最新 RAG 技术”为目标，而是围绕真实企业知识应用场景，从最基础的文档输入、检索和问答开始，通过版本迭代逐步构建文档智能、先进检索、企业工程化、RAGOps 与智能化能力。

---

## 2. 产品愿景

让企业能够将分散在 PDF、Word、Excel、PPT、Markdown、网页、扫描件等不同载体中的知识，转化为：

- 可解析
- 可管理
- 可检索
- 可追溯
- 可评估
- 可权限控制
- 可持续优化

的 AI 知识资产。

UltimateRAG 最终希望解决的不是：

> “如何实现一个 RAG Demo？”

而是：

> **“如何构建一套真正可以持续演进、能够接入企业实际知识体系的 RAG 基础平台？”**

---

## 3. 产品定位

UltimateRAG 定位为：

> **面向企业知识场景的模块化、可扩展 RAG 平台。**

它位于：


UltimateRAG 不只是一个 Chat UI，也不只是一个向量检索 Demo，而是逐渐承担以下能力：

```text
Document Intelligence
文档智能

Retrieval
检索

Generation
生成

Evaluation
评估

Security
权限与安全

Observability
可观测性

RAGOps
持续优化
```

## 4. 核心问题

现实中的企业知识通常存在以下问题。

### 4.1 文档格式复杂

企业知识可能来自：

- Markdown
- PDF
- 扫描 PDF
- Word
- Excel
- PowerPoint
- HTML
- 图片
- OCR 文档
- 数据库
- 企业内部系统

不同文档的解析方式完全不同。

UltimateRAG 将通过统一文档模型和 Parser Plugin 机制，把不同来源转换为统一的数据结构。

---

## 4.2 企业知识无法直接被大模型使用

企业数据具有：

- 私有性
- 实时变化
- 大规模
- 强业务属性

无法简单依靠大模型训练数据解决。

UltimateRAG 使用 RAG：

> Retrieval-Augmented Generation
> 检索增强生成

在回答问题之前从企业知识库中检索相关内容，再交由大模型生成答案。

---

## 4.3 单纯向量检索效果有限

现实问题可能包含：

- 专业术语
- 产品编号
- 制度名称
- 精确数字
- 模糊自然语言
- 跨章节问题
- 多文档关联

因此 UltimateRAG 会逐步支持：

```text
Dense Retrieval
稠密向量检索

Sparse Retrieval
稀疏检索

Hybrid Retrieval
混合检索

Metadata Filtering
元数据过滤

Query Rewrite
查询改写

Rerank
重排序
```

---

## 4.4 企业 RAG 不仅是“回答正确”

真实企业系统还必须解决：

```text
谁能够看到哪些知识？

文档更新后怎么重新索引？

文档删除后向量怎么删除？

解析失败怎么办？

一次回答用了哪些知识？

为什么这次回答错了？

升级模型之后效果变好还是变差？

系统一次请求成本多少？

检索和生成分别耗时多少？
```

因此 UltimateRAG 最终会逐步引入：

- ACL 权限
- 文档生命周期
- 异步任务
- Evaluation
- Trace
- Metrics
- RAGOps
- 安全防护

# 6. 核心产品原则

## 6.1 先完成，再复杂

UltimateRAG 不追求第一版就是所谓“企业级终极架构”。

每个大版本都必须：

> **独立可运行、可使用、可演示。**

先建立完整闭环，再通过版本解决上一阶段出现的问题。

---

## 6.2 核心能力与外部实现解耦

例如文档处理：

```text
RAG Core

   ↑

Unified Document Model

   ↑

Parser Interface

   ↑

Markdown / PDF / MinerU / OCR / Excel
```

UltimateRAG Core 不应该关心：

> 文档到底是 MinerU 解析的还是 Docling 解析的。

---

## 6.3 插件化

未来不同能力应该可以独立接入。

例如：

```text
Parser Plugin

MarkdownParser
PDFParser
MinerUParser
OCRParser
ExcelParser
```

以及未来：

```text
Embedding Adapter

VectorStore Adapter

Reranker Adapter

LLM Adapter
```

避免核心代码绑定具体厂商或框架。

---

## 6.4 数据与索引分离

UltimateRAG 将明确区分：

```text
原始文件
→ MinIO

业务数据 / 文档元数据
→ PostgreSQL

向量索引
→ Milvus
```

其中：

> PostgreSQL + Object Storage 是业务事实数据。

Milvus 是：

> **Derived Index（派生检索索引）**

必要情况下可以重新构建。

---

## 6.5 可解释

RAG 不应该只返回一个答案。

UltimateRAG 应逐步提供：

```text
答案

来源文档

章节

Chunk

页码

检索分数

Rerank 分数
```

让用户和开发者能够知道：

> **答案从哪里来。**

---

## 6.6 可评估

UltimateRAG 不接受：

> “感觉这个版本效果更好了。”

最终所有重要 RAG 改动都应该能够通过数据进行验证。

例如：

```text
Recall@K

MRR

NDCG

Faithfulness

Correctness

Latency

Token Cost
```

# 8. V1.0 产品定位

## Naive RAG

UltimateRAG V1.0 的目标只有一个：

> **完成一个真正可以运行和使用的最小 RAG 产品。**

完整链路：

```text
用户上传 Markdown
        ↓
MinIO 保存原文件
        ↓
PostgreSQL 保存文档信息
        ↓
Markdown Parser
        ↓
Document / Block
        ↓
Chunk
        ↓
BGE-M3 Embedding
        ↓
Milvus
        ↓
用户问题
        ↓
Vector Retrieval
        ↓
Context Builder
        ↓
LLM
        ↓
答案 + 来源引用
```

V1.0 包含：

- Web 前端
- 知识库
- 文档上传
- Markdown 解析
- Chunk
- Embedding
- Milvus 检索
- RAG Chat
- Citation
- 文档列表
- 基础检索结果查看

基础设施：

```text
Next.js

FastAPI

PostgreSQL

MinIO

Milvus

Attu

BGE-M3

LLM
```

V1.0 明确不解决：

- PDF
- OCR
- Hybrid Search
- Reranker
- Agent
- GraphRAG
- ACL
- RAGOps

这些问题留给后续版本。

```text
      ↓

┌───────────────┬───────────────┬───────────────┐

```

# 10. 后续版本方向

UltimateRAG 后续按照“解决真实问题”的方式持续演进。

## V3.0 — Advanced Retrieval

解决：

> **搜得到，但是搜得不准。**

包括：

- Dense Retrieval
- Sparse Retrieval
- Hybrid Search
- RRF
- Reranker
- Query Rewrite
- Metadata Filtering
- Parent-Child Retrieval

---

## V4.0 — Enterprise RAG

解决：

> **可以用，但是还不能真正进入企业。**

包括：

- Document Lifecycle
- Async Pipeline
- Retry
- DLQ
- ACL
- Knowledge Base Permission
- Document Version
- Audit Log
- Security

---

## V5.0 — RAGOps

解决：

> **系统上线以后如何持续优化。**

包括：

- Golden Dataset
- Retrieval Evaluation
- Generation Evaluation
- Regression Test
- Trace
- Bad Case
- Feedback
- Cost
- Latency
- Monitoring

---

## V6.0 — Intelligent RAG

根据业务场景按需引入：

- LangGraph
- Query Router
- Agentic RAG
- Tool Calling
- Self-RAG
- GraphRAG
- Multi-Agent

这一阶段不是所有企业 RAG 的必经阶段。

它只在：

> **业务问题确实需要动态决策、复杂推理或者关系检索时使用。**

# 12. 产品差异化

UltimateRAG 强调四个关键词：

### Evolvable

**可演进。**

每个版本解决上一阶段真实暴露的问题。

---

### Modular

**模块化。**

Parser、Embedding、VectorStore、LLM、Reranker 等核心能力通过接口解耦。

---

### Observable

**可观测。**

能够理解一次 RAG 请求到底发生了什么。

---

### Measurable

**可量化。**

系统效果通过 Evaluation 进行验证，而不是依靠主观感觉。

---

# 13. 产品边界

UltimateRAG 不追求：

- 成为通用大模型训练平台
- 替代 Elasticsearch / Milvus 等基础设施
- 成为模型微调框架
- 为了技术先进而强行使用 Agent
- 为了 GraphRAG 而 GraphRAG
- 第一版就模拟亿级企业生产环境

UltimateRAG 更关注：

> **在合理工程复杂度下，建立一套真实、完整、可演进的企业 RAG 架构。**

---

# 14. 项目最终目标

UltimateRAG 希望最终形成：

> **一个能够实际部署给企业内部使用，同时又能够清晰展示现代 RAG 系统架构与演进过程的开源项目。**

它既是一套软件，也是一套：

> **RAG Engineering Reference Architecture**

即：

> **RAG 工程参考架构。**

开发者不仅能够运行 UltimateRAG，还能够通过项目理解：

```text
为什么需要 Document Intelligence

为什么需要 Hybrid Retrieval

为什么需要 Reranker

为什么需要 ACL

为什么需要 Evaluation

为什么需要 Observability

为什么需要 RAGOps

什么时候才需要 Agentic RAG

什么时候应该使用 GraphRAG
```

这也是 UltimateRAG 最核心的价值。

---

## 一句话总结

> **UltimateRAG 是一个以真实企业知识场景为目标，从 Naive RAG 起步，通过模块化文档处理、高质量检索、企业工程化和 RAGOps 持续演进的开源 RAG 平台。**
