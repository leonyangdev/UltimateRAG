# UltimateRAG 技术架构文档

## 1. 文档目的

本文档用于定义 UltimateRAG 的整体技术架构、核心模块、技术选型、数据流、扩展机制和版本演进方向。

UltimateRAG 的技术目标不是一次性构建一个复杂的“大而全”系统，而是：

> 从一个最小可运行的 Naive RAG 产品开始，逐步演进为具备文档智能、先进检索、企业工程能力、评估体系和 RAGOps 能力的企业级 RAG 平台。

核心原则：

- V1.0 必须快速形成完整产品闭环
- 后续能力通过模块化方式逐步接入
- 文档解析、Embedding、VectorStore、LLM、Reranker 等能力保持可替换
- RAG Core 不强绑定 LangChain、LangGraph 等特定框架
- PostgreSQL / MinIO 保存事实数据，Milvus 作为可重建的检索索引
- 每个大版本必须独立可运行、可演示

# 10. SourceLocator

SourceLocator 负责：

> 描述内容在原始文件中的位置。

不同文档实现不同定位方式。

Markdown：

```json
{
  "heading_path": ["RAG", "Embedding", "BGE-M3"]
}
```

PDF：

```json
{
  "page": 12,
  "bbox": [100, 220, 650, 900]
}
```

Excel：

```json
{
  "sheet": "2026销售数据",
  "range": "A12:F30"
}
```

这样未来 Citation 不需要针对各种文件重新设计。

# 13. Chunk Architecture

Chunk 与 Parser 分离。

流程：

```text
Parser
   ↓
ParsedDocument
   ↓
Chunker
   ↓
Chunk[]
```

接口：

```python
class Chunker(Protocol):

    async def split(
        self,
        document: ParsedDocument,
    ) -> list[Chunk]:
        ...
```

V1.0 使用：

> Structure-aware Markdown Chunker

优先根据：

```text
Heading
Section
Paragraph
```

进行切分。

超过 Token 限制时，再进行 Token Split。

避免简单：

```text
500 字符
+
100 overlap
```

成为永久实现。

# 29. LangChain 定位

UltimateRAG 可以使用 LangChain。

但原则是：

> LangChain 是 Adapter / Tool，不是 UltimateRAG 的领域核心。

允许：

```text
LangChain Prompt

LangChain Model Adapter

LangChain Utility
```

但核心模型不要设计为：

```text
LangChain Document
```

核心 Retrieval 不应该只能通过：

```text
LangChain Retriever
```

执行。

这样 UltimateRAG 不会变成：

> LangChain Demo。

---

V1.0 不使用 LangGraph。

```text
→ Embed
→ Index
```



时再增加：

```text

```

> V6 Intelligent RAG

而不是 Core 必需依赖。

# 44. 架构核心思想总结

UltimateRAG 最重要的不是具体使用：

```text
BGE-M3

Milvus

FastAPI

MinerU
```

而是建立稳定架构边界：

```text
DocumentParser
      ↓
Unified Document Model
      ↓
Chunker
      ↓
Embedder
      ↓
VectorStore
      ↓
Retriever
      ↓
ContextBuilder
      ↓
LLM
```

任何一层未来都应该能够替换。

最终达到：

```text
Parser 可插拔

Chunk Strategy 可插拔

Embedding Model 可替换

Vector DB 可替换

Retriever 可组合

Reranker 可插拔

LLM 可替换

Workflow 可演进
```

---

# 45. 最终技术架构定位

UltimateRAG 的目标不是构建：

> 一个依赖某个 RAG Framework 才能运行的应用。

而是：

> **建立一套具有清晰领域模型、模块边界、数据边界和扩展能力的企业 RAG Reference Architecture。**

最终：

```text
Framework 可以换

模型可以换

Vector DB 可以换

Parser 可以换

LLM 可以换

RAG Strategy 可以换
```

而：

> **UltimateRAG 的核心架构仍然成立。**
